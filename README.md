# OpenWalk

OpenWalk is a mobile-first, offline-capable web map that helps people find their way
around a place on foot using their phone's GPS. Open it in a browser, allow location,
search for a building or a service, and get a walking route drawn on the map.

OpenWalk is generic by design. The application knows nothing about any particular
place. A campus, a park, museum grounds, or a fairground is a **site**: a directory of
configuration and data that the same code renders. Adding a site means adding a
directory and running the data pipeline; the application code does not change.

## How it works

- **Static site.** nginx serves a bundle of HTML, JavaScript, map tiles, and site data.
  There is no application server in version 1. Map tiles are a single PMTiles file per
  site, read by HTTP range requests, so no tile server is needed either.
- **Everything runs in the browser.** Map rendering (MapLibre GL JS with self-hosted
  vector tiles), routing, search, and all personalization happen on the device.
- **Privacy by construction.** A user's position never leaves the phone. No request
  carries coordinates, so there is nothing to log or breach. No analytics, no
  third-party scripts.
- **Offline after first load.** Installed to the home screen, the app keeps working
  without a network connection.

## The site model

Each site is a directory, `sites/<site-id>/`, with this content:

| File                                               | Purpose                                                            |
| -------------------------------------------------- | ------------------------------------------------------------------ |
| `site.yaml`                                        | Name, boundary, default view, categories, numbers, attribution     |
| `places.yaml`                                      | Curated places: numbers, names, keywords, category, entrance       |
| `overlay/`                                         | An optional official map image and its georeference                |
| `imagery/`                                         | An optional aerial photograph of the site, fetched by the pipeline |
| `raw/`                                             | Downloaded source data (treated as data only)                      |
| `places.geojson`, `walkways.geojson`, `graph.json` | Generated by the pipeline                                          |
| `basemap.pmtiles`                                  | The site's base map tiles, extracted by the pipeline               |

This repository ships one example site. A real site is its own repository, cloned into
`sites/` for local work and ignored by git here, so an institution's names, coordinates,
and map images never enter this repository's history. To deploy a site, its repository
builds an image from the generic web image and copies the site directory in.

## Adding a site

A site is built with the Python pipeline in `tools/pipeline/`; its README covers the
one-time setup. The example site under `sites/tuscawilla-park/` shows every file
described here. Paths below are relative to the repository root.

1. **Create the site directory.** A real site is its own repository cloned to
   `sites/<site-id>/`; the id is lowercase words joined by hyphens.
2. **Write `site.yaml`.** The id, a display name, the boundary as an OpenStreetMap way
   or relation id or a south-west-north-east bounding box, and the default view. Each
   site installs to a phone's home screen as its own app; a long name is cut off under
   the icon, so give it a `short_name` of about 12 characters. To have the
   privacy page say who runs the site, add `operator` with a `name` and, if you
   wish, an `email` or an https `url` to reach them. To give the app a Safety
   panel, add `safety`: a list of telephone numbers for someone who needs help,
   each with a `label`, a `number` and, if you wish, a short `note`. The numbers
   are the site's to choose, emergency services included, since they differ from
   one country to the next.
   `packages/schema/schemas/site.schema.json` lists every setting.
3. **Fetch OpenStreetMap data.** `openwalk-pipeline fetch sites/<site-id>` queries the
   Overpass API for everything inside the boundary and caches the result in `raw/`.
   The cache is reused until `--refresh` is given. Commit it if the license allows, as
   the example does: OpenStreetMap data is ODbL.
4. **Build.** `openwalk-pipeline build sites/<site-id>` writes `walkways.geojson` and
   `graph.json`, then `places.geojson` and `overlays.json` once their inputs exist. It
   reports ways excluded as unpaved, places whose entrance is far from any walkway,
   and whether the network is in one piece.
5. **Write `places.yaml`.** Every destination: an id, a name, a category, search
   keywords, and a position given as an OpenStreetMap element or a hand-placed
   location. Directions end where the place meets the nearest walkway unless you say
   where its doors are: give one as `entrance`, or several as `entrances`, and the
   app leads to whichever is the shortest walk from where the person stands. Mark
   each `verified: true` only after checking it on foot. Rebuild. To give a category a one-tap "nearest" button on the map, list it
   under `nearest` in `site.yaml` with the label the button should show; nearest is
   measured by walking distance over the network. The map colors each place by
   its category and its legend lists them; list the categories under `categories` in
   `site.yaml` to give each a readable name and set their order, which also decides
   their colors.
6. **Check it on a map.** `openwalk-pipeline debug sites/<site-id>` writes
   `debug.html`, a page that draws everything over satellite imagery. Clicking the map
   prints coordinates in the order the YAML files use; the view is kept in the URL
   hash so a spot can be linked to, and `?hide=overlay,places` opens with layers off.
7. **Close gaps in the network.** A network can be in one piece and still send people
   a long way round, because two paths that meet on the ground do not meet in the
   data. `openwalk-pipeline gaps sites/<site-id>` lists the likely spots: dead ends
   that stop a few meters short of another walkway, and walkways that cross without
   sharing a point. Each is given with its coordinates and the distance a person is
   routed today to get round it, longest first, and the debug page shows each by its
   number. Both commands take `--max-gap` to look further than a few meters. Where a connection exists on the ground, draw it in `walkways.yaml` with
   those coordinates. Each end within a few meters of a mapped walkway is joined to
   it. Setting `walkways.join_crossings` in `site.yaml` joins every ground-level
   crossing at once; bridges, tunnels and ways on another layer are left apart. Mapping the connection in OpenStreetMap afterwards is the lasting fix.
8. **Extract the base map.** Set `tiles.source` in `site.yaml` to the URL of a
   planet-wide PMTiles archive, such as a dated Protomaps basemap build, and run
   `openwalk-pipeline tiles sites/<site-id>`. It writes `basemap.pmtiles` holding only
   the tiles that cover the site's data plus a margin. The archive's attribution is
   kept and shown on the map.
9. **Add an official map, optionally.** Put a PNG of it under `overlay/` and list
   control points in `site.yaml`: a pixel in the image paired with the OpenStreetMap
   element or position it depicts. The build fits the image to the ground and reports
   the residual error in meters. Permission from the map's owner is needed to display
   it. Until you have it, give the overlay `publish: false`: it stays in the debug
   page for placing things and is left out of the image.
10. **Add an aerial photograph, optionally.** Name an imagery service under `imagery`
    in `site.yaml`, with the credit to show, and run
    `openwalk-pipeline imagery sites/<site-id>`, then build again. One picture covering
    the site is fetched and stored under `imagery/`, and the map offers it as a layer.
    It is served with the rest of the site's data, so it works with no network and no
    phone contacts the imagery service. The service must be an ArcGIS ImageServer, and
    the imagery must be yours to redistribute: government orthoimagery often is.
    A photograph from any other source is added the way an official map is, in the
    step before: put the picture under `overlay/` as a PNG with control points, and
    the build fits it to the ground.

Which ways count as walkways is set per site under `walkways` in `site.yaml`:
the highway values admitted, surface values treated as unpaved, whether parking aisles
and which minor roads may be walked as a last resort, and the snapping distance for
hand-drawn ways.

## Repository layout

```
apps/web/          the browser app (Vite + TypeScript, no framework)
packages/routing/  pedestrian routing: graph, snapping, shortest paths (pure, tested)
packages/search/   fuzzy search over a site's places (pure, tested)
packages/schema/   shared schemas for pipeline output and the app
e2e/               browser tests of the built app (Playwright)
sites/             the example site; real sites are separate repositories
tools/pipeline/    Python data preparation
deploy/            Dockerfile, compose file, nginx config
docs/              requirements, architecture, device testing
```

## Developing

Requires Node 24 (`.nvmrc`) and Docker with the compose plugin.

```
npm ci              # install exact versions from the lockfile
npm run dev         # Vite dev server for apps/web
npm test            # Vitest across every workspace
npm run check       # lint, format check, typecheck, test: what CI runs
npm run build       # production bundle in apps/web/dist
docker compose -f deploy/compose.yaml up --build   # nginx serving the bundle
npm run test:e2e    # browser tests against that running stack
```

The browser tests (`e2e/`, Playwright) drive the built app the way a person would:
search, directions with a pretended position, arrival, being away from the site,
installing, working with no network, and automated accessibility checks. One test
watches every request the page makes and fails if any leaves the site or carries a
position. They read their places from the example site, so they hold no site facts.
Before the first run, `npx playwright install chromium webkit` in `e2e/` downloads the
two browser engines.

The same tests can check a site once it is deployed, behind whatever network serves
it, which is where a script or request added on the way would show up:

```
E2E_BASE_URL=https://maps.example E2E_SITE=<site-id> npm run test:e2e -- privacy install
```

`E2E_SITE` names the site's directory under `sites/`, which the tests read for places
and positions.

The dev server serves every directory under `sites/` at `/sites/<site-id>/`, and the
map for a site is at `/s/<site-id>/`, for example
`https://localhost:5173/s/tuscawilla-park/`. The root address lists the sites a host
serves, or opens the site directly when there is only one. An image carries one site
or several, chosen with `--build-arg SITES="<site-id> <site-id>"` and defaulting to
the example site.

The image takes from each site only the generated files the app reads: its settings,
places, walkways, graph and base map, any overlays, and recorded traces. The
hand-written sources, the checking page and anything else in the site's directory are
left out, so they are never served.

The base map's fonts and icons are served by the app itself from
`apps/web/public/basemap/`, so no third-party host is contacted. They cover Latin,
Greek, Cyrillic, Hebrew and Arabic scripts; `tools/basemap-assets/fetch.sh` fetches
more glyph ranges for a site whose labels need another script.

Testing on a real phone, including HTTPS on a local network, is described in
`docs/DEVICE_TESTING.md`. See `CONTRIBUTING.md` before opening a pull request.
